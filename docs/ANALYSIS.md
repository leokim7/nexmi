## 1. 프로젝트 개요 분석

### 1.1 한 줄 정의

같은 플랫폼 안에서 두 그룹에게 서로 다른 질문에 답한다.

| 그룹 | 질문 | 계산 | 출력의 성격 |
|---|---|---|---|
| 재직자 | “내 직업 예상 종료일은?” | `engine.simulate` (모델 1.2.0-seed) | 3가지 가정별 **현재 업무 방식의 전환 연도**(해고일 아님) |
| 진로 고민자(중·고·대·취준) | “나에게 맞는 진로·직업은?” | `student_engine.diagnose` (1.5.0-explorer-seed) | **탐색 적합지수**(적성 확률 아님) + 체험·학습 경로 |

채용공고·기업 매칭·입사지원은 범위 밖. 두 결과를 합친 통합 점수는 만들지 않는다.

### 1.2 보유 자산

| 자산 | 규모 | 상태 |
|---|---|---|
| 직군 | 50개 (9개 영역) | 공식 직업분류 코드 미매핑 |
| 업무 | 700개 (직군당 14) | 저자 설계값, 전문가 검토 전 |
| 체험 | 100개 (직군당 2) × 학령 4단계 변형 | 가상 사례 전용 |
| 관심 축 / 역량 | 8개 / 10개 | 서비스 자체 설계 |
| 엔진 테스트 | 재직자 12 + 진로 13 | 모두 통과 (이번 작업에서 재확인) |
| 화면 명세 | 진로 25 + 재직자 19 + 지속방문 7 + 진입 1 = 52 | 구현 계약 |

### 1.3 기획서가 강하게 요구하는 원칙 (구현 시 지켜야 할 제약)

1. **정직성**: 확률·신뢰구간·백분위·직군 평균을 만들지 않는다. null 은 null 로(“2040년까지 기준 미도달”, “아직 모름”, “자료 없음”을 서로 다른 문구로).
2. **엔진 불변**: 계수를 UI 편의로 바꾸지 않는다. LLM 으로 점수·날짜를 만들지 않는다.
3. **분리**: 관심(순위) ↔ 준비 수준(순위 미반영), 개인 변화 ↔ 모델 변화, 원본 결과 ↔ What-if 초안.
4. **저장 동의**: 기본은 현재 탭 메모리. 기기 저장·계정 저장은 명시적 선택 후.
5. **지속 방문은 행동 중심**: 가짜 피드·날짜 흔들기·공포 카운트다운 금지. 과제·기록은 점수에 자동 가산하지 않는다.

### 1.4 분석하며 발견한 문제 (의사결정 필요)

**① 재직자 핵심 헤드라인이 거의 항상 “미도달”로 나온다 — 가장 중요**

현재 모델로 50개 직군을 직접 계산해본 결과:

| 조건 | 2040년까지 ‘종합 재편 지수 60’ 도달 직군 |
|---|---|
| 기본 업무분포 · 미들 · 개인 도입 · 역할 6개 모두 50 · 기준 가정 | **0 / 50** |
| 기본 업무분포 · 주니어 · 에이전트 도입 · 역할 모두 0 · **빠른 변화** | **0 / 50** (최대 59.1) |
| 극단값: 단일 업무(‘자료 입력’) 100% · 에이전트 · 역할 0 · 빠른 변화 | 65.2 (유일하게 도달) |

즉 서비스의 대표 질문(“내 직업 예상 종료일은?”)에 대해 사실상 모든 사용자가 **“2040년까지 기준 미도달”**을 보게 된다. 정직한 출력이긴 하지만 제품 가치가 약해진다. 선택지(모두 모델 버전 발행이 필요한 결정):

- (a) 전환 기준(60) 또는 계수 재보정 → 모델 1.3 발행·검증
- (b) 헤드라인을 ‘업무 재편 시작(자동화 압력 30)’ 연도로 바꾸기 — 이 값은 직군·가정별로 실제로 달라짐(예: SW개발자 2030/2032/2038)
- (c) 현행 유지 + ‘미도달’ 의미를 더 강조 (현재 구현)

현재 구현은 (c)이면서, 결과 상단에 세 전환점(AI 보조 본격화 / 업무 재편 시작 / 업무 방식 전환점)을 항상 함께 보여줘 (b)의 정보가 바로 보이게 했다.

**② 진로 추천의 구별력이 낮다**

무작위로 8개 축에 모두 답한 프로필 200개 중 **200개 모두** 상위 5개 후보 안에 동점이 생겼다. 같은 영역 직군들이 동일한 관심 태그를 공유하기 때문(모델 README 도 인정). UI는 “동점은 ID 순, 우열 아님”을 명시하고, 순위 번호를 표시하지 않으며, 체험 반응(30%)으로 구별하도록 체험을 다음 행동의 중심에 두었다. 근본 해결은 모델 쪽(추가 문항·업무 단위 관심)이다.

**③ 화면 분절이 과도하다 (52개)**

입력 한 항목마다 별도 화면(재직자 입력 6화면 + 처리 화면), 저장·설정·리포트가 모드별로 중복, 지속방문 7화면이 별도 허브. 모바일에서 단계가 많을수록 이탈이 늘고, 같은 기능이 두 곳에 있으면 데이터 위치가 헷갈린다. → 2장에서 재구성.

**④ 그 밖의 기술 이슈**

- 재직자 결과 원본이 약 300KB(3가정×15년×14업무). 화면에 필요한 부분(전 연도 지표 + 4개 연도 업무)만 남겨 기기 저장 용량 문제를 피함.
- 시안 HTML 은 데이터 900KB를 페이지에 내장. 운영 구현은 `/api/catalog` 로 분리(gzip 25KB).
- 엔진 수치는 Python 3.14↔3.12 사이에 마지막 자리 부동소수(1e-14)만 다름 → parity 테스트는 1e-9 허용오차로 비교.

## 2. 사용자 편의를 위한 구조 개선

### 2.1 원칙

1. **한 흐름 = 한 화면 묶음**: 입력은 단계형 흐름(진행 표시·뒤로 가기·입력 보존), 결과는 탭으로 묶는다.
2. **모바일 하단 5탭**: 홈 · 직업 미래 · 진로 탐색 · 실천 · 내 기록. 데스크톱은 상단 내비.
3. **중복 제거**: 저장·설정·이력·리포트는 모드 공통 ‘내 기록’ 한 곳에서 모드별로 관리.
4. **기본값은 숨기지 않고 표시**: 업무 비중 임시 분포는 ‘확인 필요’ 배지, 역할 6문항은 기본값 없이 응답 필수.
5. **실패와 정보 부족을 다르게**: 계산 실패(재시도) ↔ 정보 부족(추가 질문 안내) ↔ 미도달(정상 결과).

## 3. 디자인 — wanjoo.kr 디자인 시스템 적용

`~/Documents/Claude/wanjoo/DESIGN-SYSTEM.md` 를 그대로 따랐다. 기획서의 녹색 토큰(`design_tokens.json`)은 대체했다.

- 버튼·칩은 알약(999px), 카드는 26px 라운드, 남색 기반 옅은 그림자. 버튼·칩 `color` 항상 명시.
- 브레이크포인트 4개(1080/980/680/400)만. 그리드는 `minmax(0,1fr)`, 카드 `min-height` 고정 없음.
- 섹션 헤더: 영문 eyebrow → 한국어 큰 제목 → 회색 보조 설명.
- 모션: 스크롤 등장 페이드업 1종 + `prefers-reduced-motion`.
- 접근성: 스킵 링크, 포커스 링, 44px 터치 영역, 라우트 이동 시 본문 포커스, 색+텍스트 병행.
- 차트는 엔진 출력이 있는 값만(전환점 타임라인, 재편지수 추이). 가정 구분은 같은 블루 계열 + 선 모양.

## 4. 아키텍처 · 배포

```
Browser (React 18 + TS, Vite)  ──fetch──▶  FastAPI (Python 3.12)
  현재 탭 메모리 (기본)                       /api/catalog            직군·업무·체험 (공개 캐시)
  localStorage (동의 시)                       /api/worker/diagnoses   engine.simulate (원본)
                                               /api/explorer/diagnoses student_engine.diagnose (원본)
                                               /*  → frontend/dist (SPA)
```

- 단일 Docker 이미지(Node 빌드 → Python 런타임), Railway `PORT` 주입, 헬스체크 `/api/health`.
- P0 는 DB 불필요(서버는 계산만, 저장 안 함). PostgreSQL(`docs/handoff/STORAGE.sql`)은 계정·공유·관리자(P1)부터 필요.
